## 1. 定位

### 1.1 hermes 是什么

**每个用户私有的校园执行器。** 它替这个人查课表、看空档、提交预约，并长期持有这个人的校园会话。

### 1.2 hermes 不是什么

- **不是聊天机器人**——它没有人格，不闲聊，不维持活跃度
- **不是撮合者**——它只服务一个人，不知道别人的存在
- **不是常驻进程**——见第 2 节

### 1.3 与阿凑的边界

```
        hermes                          阿凑
  ┌──────────────────┐          ┌──────────────────┐
  │ 服务对象：一个人   │          │ 服务对象：一个局   │
  │ 持有：个人凭证     │          │ 持有：匿名意图池   │
  │ 原则：越常用越好   │          │ 原则：越早退场越好 │
  └────────┬─────────┘          └─────────┬────────┘
           │                              │
           └────── Action Schema ─────────┘
                   （唯一通信面）
```

**硬边界：阿凑永远拿不到任何用户的凭证，只能提交语义动作请求。** 两者不共享状态、不互相持有引用。

## 2. 形态决议：一份状态 + 无状态执行器

### 2.1 为什么不能每人一个常驻进程

| 问题 | 后果 |
|---|---|
| 6 万用户 × 常驻 Node 进程 | 内存与调度成本不可承受 |
| 99% 时间无请求 | 资源全部空转 |
| 进程内持有会话 | 进程崩溃即丢登录态，恢复要重新扫码 |

### 2.2 正确形态

```
┌─── 每用户持久化（有状态，长期存在）───────────────┐
│  Vault：凭证 + 会话文件 + 授权范围 + 健康状态       │
│  Cache：课表 / 培养方案 / 能力向量（结构化落库）    │
└──────────────────────────────────────────────────┘
                      ↑ 按需挂载
┌─── 全局执行器池（无状态，用完即弃）───────────────┐
│  拉起进程 → 挂载单个用户状态仓 → 执行 → 回收        │
└──────────────────────────────────────────────────┘
```

**"每人一个 hermes"是产品语义**：用户感知上他有一个私人助理。**部署上是共享执行池 + 私有状态仓。**

### 2.3 三个组成部分

| 组件 | 职责 | 有无状态 |
|---|---|---|
| **Vault** 状态仓 | 凭证隔离、生命周期、健康巡检、撤回清除 | 有状态，每用户一份 |
| **Executor Pool** 执行器池 | 进程拉起、并发控制、超时、限流、熔断、幂等 | 无状态，全局共享 |
| **Session Orchestrator** 登录编排器 | 扫码登录的异步长任务编排 | 有状态，每登录会话一份 |

## 3. 底座：sysu-anything CLI

### 3.1 三个可直接复用的机制

| 机制 | 价值 |
|---|---|
| **`--state-dir <dir>`** | 多租户隔离**不需要改 CLI 核心**，一人一目录即可 |
| **写操作默认预览、`--confirm` 才提交** | 与 F10 三段式**天然同构**，安全语义白捡 |
| **`--json` 纯 JSON 输出** | 可被服务端直接消费，无需解析人类可读文本 |

### 3.2 已知缺口（落地前需补）

| 缺口 | 影响 | 处理 |
|---|---|---|
| `matrix` 不支持 `--state-dir` | 作业 DDL 无法多租户 | **必须补齐**，否则冲刺局场景无法上线 |
| 各命令 `--json` 覆盖率未知 | 部分能力需解析文本 | 逐命令实测，缺失的补 |
| 无批量/并发保护 | 并发调用可能互相污染状态文件 | 由执行器池加用户级串行锁 |
| 无统一错误码 | 失败原因难以分类处理 | 在适配器层归一化，见 6.4 |

## 4. 多租户状态仓（Vault）

### 4.1 目录布局

```
/var/lib/onemore/vaults/
├── u_{user_id}/
│   ├── session.json            CAS / appgw 会话
│   ├── jwxt-session.json       教务
│   ├── libic-session.json      图书馆空间
│   ├── gym-session.json        场馆会话
│   ├── gym-auth.json           场馆 token
│   ├── explore-session.json    交叉探索
│   ├── career-session.json     就业系统
│   ├── matrix-session.json     作业系统
│   └── _meta.json              授权范围、健康状态、最后校验时间
```

> 布局与 CLI 默认状态目录一致，因此挂载时只需 `--state-dir /var/lib/onemore/vaults/u_{id}`。

### 4.2 隔离原则

1. **一次执行只挂载一个用户的状态仓**——执行器进程无法看到其他目录
2. **状态仓目录权限最小化**，执行器以低权限用户运行
3. **静态加密**：会话文件落盘加密，执行前解密到临时挂载点，执行后销毁
4. **业务服务无读权限**——`onemore-server` 只能调 Action Schema，不能读 Vault

### 4.3 `_meta.json` 结构

```json
{
  "user_id": "u_10023",
  "grants": {
    "timetable":    { "granted": true,  "at": "2026-08-11T10:00:00+08:00" },
    "curriculum":   { "granted": true,  "at": "..." },
    "enrollment":   { "granted": true,  "at": "..." },
    "agent_booking":{ "granted": false, "at": null }
  },
  "sessions": {
    "cas":   { "healthy": true,  "last_checked": "...", "expires_hint": "..." },
    "libic": { "healthy": false, "last_checked": "...", "last_error": "code:300" }
  },
  "revoked_at": null
}
```

### 4.4 撤回与清除

用户在 App 内撤回任一授权项时：

1. `_meta.json` 中该项置 `granted: false`
2. 删除对应的会话文件
3. **同步清除由该授权派生的数据**（撤回课表 → 删除课表缓存与空档索引 → 该用户退出所有依赖时间匹配的意图池）
4. 若撤回"代理预约"，所有处于 `Previewed` 的动作立即作废

## 5. Action Schema 白名单

### 5.1 为什么 LLM 绝不能拼命令行

| 风险 | 说明 |
|---|---|
| **注入面** | 用户自然语言最终变成 shell 参数，`--confirm` 可被诱导注入 |
| **不可复现** | 同一句话两次生成不同命令，无法测试与回归 |
| **不可审计** | 出问题后无法回答"当时到底执行了什么" |
| **越权执行** | LLM 自主附加 `--confirm` 即构成未经授权的真实预约 |

### 5.2 唯一收窄点

```
自然语言
   ↓ [LLM]           只产出结构，不产出命令
Action Schema        强类型 · 枚举 · 白名单 · 无自由文本字段进入命令行
   ↓ [确定性代码]     参数校验 → 授权校验 → 分级校验 → 转译
CLI 调用             参数全部经过转义，--confirm 由业务条件决定
```

### 5.3 Schema 形态

```python
class ActionRequest:
    action: ActionName          # 枚举，白名单内
    user_id: str
    params: dict                # 每个 action 有独立的强类型 schema
    gathering_id: str | None    # 黄灯动作必填
    confirm: bool               # 客户端与 LLM 永远传 False；仅服务端可置 True
    idempotency_key: str
```

**`confirm` 字段的写入权限在服务端**：请求体里带上来的 `confirm=true` 一律忽略并记为安全事件。

### 5.4 动作目录

| 语义动作 | 档 | CLI 映射 | 服务的功能点 |
|---|:---:|---|---|
| `timetable.fetch_term` | 🟢 | `jwxt timetable --scan-from 1 --scan-to 25 --json` | F2 F8 课表 ETL |
| `timetable.today` | 🟢 | `today --json` | 今日视图 |
| `timetable.section_times` | 🟢 | `jwxt section-times --json` | 空档计算的节次基准 |
| `assignment.list_unfinished` | 🟢 | `matrix assignments list --unfinished --json` | F5 DDL 触发、5.3 冲刺局 |
| `room.available` | 🟢 | `libic available --kind --date --json` | F8 场地联合空档 |
| `room.room_types` | 🟢 | `libic room-types --json` | 房型选择 |
| `room.reserve_preview` | 🟡 | `libic reserve ...`（**不带** `--confirm`） | F10 预览 |
| `room.reserve_commit` | 🟡 | `libic reserve ... --members ... --confirm` | F10 团体预约执行 |
| `gym.available` | 🟢 | `gym available --venue-type --json` | 运动搭子空场 |
| `gym.book_preview` | 🟡 | `gym book ...`（不带 `--confirm`） | F10 预览 |

| `seminar.list` | 🟢 | `explore seminar list --json` | 科研连接 |

| `career.teachin_list` | 🟢 | `career teachin list --json` | **免登录，冷启动库存** |
| `career.jobfair_list` | 🟢 | `career jobfair list --json` | **免登录，冷启动库存** |

**🔴 红灯：不存在对应语义动作，适配器层无实现。**
`jwxt leave apply` · `career job apply` · `career * signup` · `xgxt workstudy apply` · `xgxt holiday apply` · 选课 · 成绩 · 支付

### 5.5 校验链（每次调用必过）

```
1. action ∈ 白名单？                    否 → 拒绝并记安全事件
2. params 通过该 action 的强类型校验？   否 → 400
3. 用户已授予所需 grant？                否 → 引导授权
4. 用户信任等级满足该动作要求？          否 → 引导至等级页（F15）
5. 黄灯动作：gathering 是否全员确认？    否 → 拒绝置 confirm
6. 幂等键是否已执行过？                  是 → 返回原结果
7. → 转译并执行
```

## 6. 执行器池

### 6.1 进程模型

```
请求 → 入队（用户级串行锁）→ 取执行槽 → 拉起进程
     → 挂载 Vault（--state-dir）→ 执行 → 采集 stdout/JSON
     → 销毁临时挂载 → 归一化结果 → 返回
```

**用户级串行锁是必须的**：同一用户的两条命令并发写同一批状态文件会互相污染。

### 6.2 资源控制

| 控制项 | 建议初值 | 理由 |
|---|---|---|
| 全局并发执行槽 | 32 | 校园系统承压能力未知，宁小勿大 |
| 单用户并发 | 1 | 状态文件互斥 |
| 单次执行超时 | 读 30s / 写 60s / 扫码登录 200s | 扫码需大于 CLI 默认 180s |
| 每用户每分钟调用上限 | 20 | 防止客户端异常轮询 |
| 对单一校园子系统的全局 QPS | 分子系统配置 | 避免被判定为异常流量 |

### 6.3 熔断

对每个校园子系统独立计数：连续失败达阈值 → 熔断该子系统 N 分钟 → 期间所有相关动作**快速失败并返回降级提示**，不排队堆积。

产品侧降级表现：
- 读操作熔断 → 用缓存数据 + 标注"数据更新于 X"
- 写操作熔断 → 局停在 `Confirmed`，不进 `Previewed`，通知用户稍后自动重试

### 6.4 失败分类

| 类别 | 判定 | 处理 |
|---|---|---|
| 登录失效 | 会话相关错误码 | 触发重新扫码流程，**不重试** |
| 资源冲突 | 时段已被占用 | 交回业务层重新选时段（F13 场地失效分支） |
| 限流/维护 | 超时、5xx | 退避重试，超限后熔断 |
| 参数错误 | 4xx | **不重试**，记为 bug 上报 |
| 未知 | 其他 | 记录原始输出，人工排查 |

**归一化是适配器层的核心职责**：上层业务只应看到这五类，不应看到任何校园系统的原始报错。

### 6.5 幂等

每个写动作携带 `idempotency_key = hash(gathering_id + action + 关键参数)`：

- 执行前写入"执行中"记录
- 成功后写入结果
- 重复请求命中已有记录直接返回，**绝不重复提交预约**

## 7. 会话生命周期

### 7.1 扫码登录编排（异步长任务）

```
App 请求授权
   ↓
服务端创建 login_session（状态 PENDING）
   ↓
执行器拉起 auth workwechat --state-dir <vault> --timeout 200
   ↓
CLI 生成二维码 PNG → 服务端读取 → 转为图片/深链推送到 App
   ↓ 状态 WAITING_SCAN
用户在企业微信扫码确认
   ↓
CLI 进程返回，会话写入 Vault
   ↓ 状态 SUCCESS → 推送客户端 → 触发课表 ETL
```

**关键约束**：此流程**不能放在一次 HTTP 请求里**。客户端通过轮询 `GET /auth/session/{id}` 或长连接获取状态。

失败分支：`TIMEOUT`（未扫码）、`CANCELLED`（用户取消）、`FAILED`（CLI 异常）——三者都要有明确的重试入口。

### 7.2 各子系统的二段登录

CAS 成功不等于所有子系统可用。多数子系统需要额外播种自己的站点会话：

| 子系统 | 播种/恢复动作 | 健康检查 |
|---|---|---|
| 教务 | 复用 CAS 自动二段登录 | `jwxt status` |
| 图书馆 | `libic refresh` | `libic whoami` |
| 场馆 | callback 回放 + `gym token refresh` | `gym profile` |
| 交叉探索 | `explore refresh` | `explore whoami` |
| 就业（写） | 由 CAS 自动播种 | 无独立 status |

**产品含义**：授权不是一个开关，是一组开关。App 的授权管理页（M4）必须按子系统展示健康状态，而不是笼统显示"已登录"。

### 7.3 健康巡检

```
每 6 小时  → 对活跃用户跑一轮各子系统 status 检查
发现失效  → 标记 _meta.json，推送"阿凑需要你重新授权一下"
临近成局  → 局开始前 T-24h 强制校验一次相关子系统
```

**必须提前巡检**，绝不能等用户点"确认预约"时才失败——那时局已经全员确认，失败代价最高。

### 7.4 失效降级

| 场景 | 表现 |
|---|---|
| 浏览、匹配、成局 | **不受影响**，继续可用 |
| 需要执行动作 | 提示重新扫码，局停在 `Confirmed` 不回退 |
| 长期失效（> 7 天） | 退出需要实时执行的匹配池，但保留历史与信任等级 |

## 8. `--confirm` 授权链路

### 8.1 与多人确认协议的绑定

```
Tentative ──全员分别确认──→ Confirmed
                              ↓ 服务端校验：members.all(confirmed) == true
                          room.reserve_preview（不带 --confirm）
                              ↓ 保存 payload 快照
                          Previewed ──用户看到预览并授权──→
                              ↓ 服务端此时才允许置 confirm=true
                          room.reserve_commit（--confirm）
                              ↓
                          Executed → 写日历（F12）
```

### 8.2 三条铁律

1. **`confirm` 只能由服务端在校验业务条件后置位**，客户端与 LLM 传入的值一律丢弃
2. **没有 Previewed 就没有 Executed**，不允许任何路径跳过预览
3. **预览快照必须落库**（`CampusAction.预览快照`），执行时比对参数是否与快照一致，不一致则中止

### 8.3 回滚

执行失败时按逆序回滚：撤回已发通知 → 删除已写日历事件 → 局回退至 `Confirmed` → 触发 F13 重新计算时段。

## 9. 课表 ETL

### 9.1 时机与范围

| 时机 | 动作 |
|---|---|
| 授权成功后立即 | `jwxt timetable --scan-from 1 --scan-to 25` 全学期一次性扫描 |
| 同时 | `jwxt section-times` 取节次时间基准 |
| 每周一凌晨 | 增量校验，比对调课/补课/退改选 |
| 用户手动下拉 | 允许，但加频率限制 |

### 9.2 落库产物

| 产物 | 供给 |
|---|---|
| 结构化课程表（含教学班） | F4 同课同学（**教学班粒度**，非课程粒度） |
| 每周可用时间窗 | F8 共同空档计算 |
| 学业节律特征 | F2 画像 |
| 课程号清单 | F2/F3 学科域映射与跨专业信号 |

### 9.3 为什么必须缓存

- 执行器每次调用要拉起进程 + 打校园系统，高频读扛不住
- 课表是**低频变更、高频读**的典型
- F8 的共同空档计算需要**多人课表同时在手**，实时查 N 个人的课表不可行

## 10. 可移植性

移植到新学校时，**只有 `adapters/` 需要重写**：

```
不变（约 90% 代码）              需重写（6–8 个适配器）
──────────────────              ──────────────────────
Action Schema 定义与校验         身份认证适配
Vault 状态仓管理                 教务适配（课表/培养方案/选课）
执行器池与资源控制               场地预约适配
会话编排与健康巡检               研讨室适配
幂等、熔断、失败归一化           活动/赛事信息源适配
课表 ETL 框架                    作业系统适配
```

**验收标准**：新学校接入时，`schema/` 与 `executor/` 目录零改动。若需要改动，说明抽象漏了。

## 11. 演进三阶段

| 阶段 | 目标 | 形态 | 判据 |
|---|---|---|---|
| **一 · 答辩/Demo** | 跑通闭环 | 单机直接调 CLI，少量真实账号，`--state-dir` 隔离 | 能完整演示 意图→匹配→多人确认→真实预约成功 |
| **二 · 小范围内测** | 可靠性 | CLI 包成 HTTP 服务，加队列、幂等、限流、会话巡检 | 执行成功率 > 95%，登录失效可自愈 |
| **三 · 规模化** | 性能 | 高频读路径改为缓存 + 直连适配器，CLI 只保留写路径 | 单次读响应 < 200ms |

**不要跳阶段。** 阶段一的价值是验证产品，不是验证架构；此时最大的风险是把时间花在还没有用户的扩展性上。

## 12. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 校园系统改版导致适配器失效 | **高** | 每个适配器配契约测试 + 每日巡检；失效时降级而非报错 |
| 被校方判定为异常流量 | **高** | 严格限流、避开高峰、遵守 robots 与服务条款、优先争取官方合作 |
| 扫码登录流失率高 | **中** | 二维码有效期内允许重发；讲清"为什么需要授权"；未授权也能浏览 |
| 会话大面积同时失效 | **中** | 分批巡检、错峰提示，避免同一时刻全员要求重新扫码 |
| `matrix` 无状态隔离 | **中** | 上线冲刺局前必须补齐 |
| CLI 单点（作者一人维护） | **中** | 能力清单与契约测试固化，适配器可被替换实现 |
| 用户误以为 hermes 能代办一切 | **低** | 红灯能力在 UI 上明确说明"这件事需要你自己去做" |
