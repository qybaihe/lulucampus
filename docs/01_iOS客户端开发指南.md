# 01 · iOS 客户端开发指南

> 对应 V2.1 产品方案
> 技术栈：Swift / SwiftUI / iOS 16+
> 本文按**页面层级**逐层拆解，每页说明承载什么功能、依赖什么接口、受什么规则约束。

---

## 1. 客户端职责边界

### 1.1 只做四件事

**输入 · 展示 · 确认 · 日历**

### 1.2 明确不做

| 不做 | 原因 |
|---|---|
| 任何匹配逻辑 | 匹配是服务端的组合优化，客户端拿不到别人的数据 |
| 任何空档计算 | 计算需要多人课表，客户端只能看到自己的 |
| 直接调用 CLI 或校园系统 | 一切经业务服务的 Action Schema 出口 |
| 持有校园密码 | 认证走企业微信扫码，全程无密码输入框 |
| 自行决定 `--confirm` | 执行授权由服务端按多人确认状态放行 |

### 1.3 两个 AI 在 UI 上物理分开

```
┌─────────────────────────────────────────────────┐
│  「今天」Tab  =  hermes 的主场                    │
│   工具属性 · 常驻 · 用得越多越好                   │
│   课表 / DDL / 场地 / 班车 / 自然语言问答          │
├─────────────────────────────────────────────────┤
│  「⊕ 差一个」  =  阿凑的入口                       │
│   媒介属性 · 成局后淡出 · 用得越少越好              │
│   意图输入 / 匹配 / 成局                          │
└─────────────────────────────────────────────────┘
```

**这个分离必须在 UI 上可感知**：hermes 是一个工具面板，阿凑是一个会消失的助手。绝不做成同一个聊天窗口。

## 3. 工程结构

```
OneMore/
├── App/                    入口、路由、深链、推送注册
├── Core/
│   ├── Network/            APIClient、错误归一化、重试
│   ├── Auth/               扫码登录状态机、会话态
│   ├── Storage/            Keychain（令牌）、SwiftData（缓存）
│   ├── Calendar/           EventKit 封装
│   └── Push/               APNs、深链解析
├── DesignSystem/           色板、字体、间距、通用组件
├── Features/
│   ├── Onboarding/         A 层
│   ├── Today/              B 层 · hermes
│   ├── OpenGatherings/     C 层
│   ├── Intent/             D 层 · 阿凑
│   ├── MyGatherings/       E 层
│   ├── Me/                 M 层
│   └── Organizer/          O 层 · T4
└── Shared/
    ├── Components/         跨层复用组件
    └── Models/             DTO 与领域模型
```

**架构**：MVVM + 单向数据流。每个 Feature 一个 `Store`（`ObservableObject`），页面只读 State、只发 Action。

## 5. A 层 · 启动与准入

> 目标：**用最少的步骤把用户从"下载了"变成"有可验证画像的 T1"**，并且全程不出现密码输入框。

### A1 · 启动路由

- **路由** `/`
- **职责** 判断落点，无 UI（仅品牌闪屏）
- **逻辑**
  ```
  无令牌            → A2
  有令牌未认证       → A3
  已认证未初始化画像  → A5
  已初始化未开社交    → B1（不强制走 A7）
  正常              → B1
  有待处理深链       → 目标页
  ```
- **要点** 冷启动 300ms 内决策完；不要为了展示品牌人为拖延

### A2 · 价值引导

- **路由** `/onboarding`
- **职责** 三屏说清产品是什么
- **三屏内容**
  1. 差一个不是交友软件，是帮你把事凑成的工具
  2. 你的课表和选课记录让匹配从第一天就准（**强调零填表**）
  3. 凑不齐没人知道，不用担心被拒绝（**降低第一次的心理成本**）
- **要点** 可跳过；**不承诺"认识新朋友"**，承诺"把事办成"

### A3 · 扫码认证 `[V2.1 已改为扫码]`

- **路由** `/auth/scan`
- **职责** 企业微信扫码完成统一身份认证
- **承载** F1
- **区块**
  1. 二维码展示区（服务端推送的图片）
  2. 倒计时与刷新按钮（有效期内可重发）
  3. 状态提示：等待扫描 / 已扫描待确认 / 成功 / 超时
  4. "为什么需要授权"折叠说明
- **交互**
  - `POST /auth/session` 创建登录会话 → 轮询 `GET /auth/session/{id}`
  - 轮询间隔 2s，最长 200s
  - 超时 → 显示重试，不显示报错堆栈
- **红线** **全页面不得有任何密码输入框**
- **要点** 这是**异步长任务**，不要在一次请求里等待；App 退到后台再回来要能恢复轮询

### A4 · 授权范围

- **路由** `/auth/grants`
- **职责** 分项授权，逐项可关
- **承载** F1 F27
- **区块**（每项独立开关 + 一句话说明 + "用来做什么"）
  | 授权项 | 文案要点 |
  |---|---|
  | 课表 | 用来算你和别人的共同空档，**别人永远看不到你的课表** |
  | 培养方案 | 用来生成你的能力标签，不用填表 |
  | 选课记录 | 用来识别你主动选修的方向，**不读成绩** |
  | 代理预约 | 允许在你确认后替你提交预约 |
- **规则** 全部可跳过；跳过后功能降级但不阻断浏览
- **要点** "不读成绩"必须显式写出来——这是最容易引发疑虑的一点

### A5 · 画像初始化进度

- **路由** `/auth/init`
- **职责** 跑课表 ETL 与画像生成，把等待时间变成价值展示
- **承载** F2 F3 决议六
- **区块** 分步进度（读取培养方案 → 扫描全学期课表 → 生成能力标签 → 识别跨专业选修）
- **交互** 每步完成即时展示成果（"识别到 42 门已修课程"）
- **要点**
  - 全学期课表扫描较慢，**必须有分步反馈**，否则用户以为卡死
  - 允许后台继续，用户可先进 B1
  - 失败可单步重试，不整体回滚

### A6 · 画像确认

- **路由** `/auth/profile-confirm`
- **职责** 展示系统生成的画像，用户确认或增删
- **承载** F2 F3
- **区块**
  1. 认证事实（学院/专业/年级/校区）——**灰显不可编辑**，标注"来自学校记录"
  2. 能力标签云——每个标签带来源 chip：`已验证·选课` / `自述`
  3. 跨专业选修高亮区——"你主动选了 3 门设计类课程"
  4. 可用时间窗预览——来自课表
- **红线** 不展示任何成绩信息
- **要点** 这一页是**产品的第一个"哇"时刻**，设计上要给足分量。用户从没填过表，却看到一份准确的自己

### A7 · 社交开关引导

- **路由** `/auth/social`
- **职责** 单独询问是否进入社交池
- **承载** F19 F24-1
- **文案要点** "你现在已经可以用课表、订场地、查作业了。要不要也让阿凑帮你凑局？"
- **规则** **默认关闭**；关闭状态下 B/M 层完全可用，C/D/E 层入口置灰并说明原因
- **要点** 这是产品最重要的一次"不推销"。认证 ≠ 社交，必须让用户主动开

### A8 · 系统权限申请

- **路由** `/auth/permissions`
- **职责** 通知与日历权限
- **时机** **不在此页一次性索要**——通知权限在首次成局时申请，日历权限在首次预约成功时申请
- **要点** 系统权限弹窗只有一次机会，必须在用户理解价值后再弹

## 6. B 层 · 今天（hermes 主场）

> 定位：**这是一个校园工具面板，不是社交页。** 用户为办事而来，社交是自然出现的第二步（F5）。

### B1 · 今天首页

- **路由** `/today`
- **职责** hermes 的主界面：今天要干什么 + 需要我处理什么 + 工具入口
- **承载** F5 F12
- **区块（自上而下）**
  1. **hermes 问答条**——常驻输入框"问问 hermes"，点击进 B2
  2. **待办区**——待确认的局（E3 深链）、待授权的动作（E5）、需重新扫码的提示（G3）
  3. **今日时间轴**——课程 + 已成局的日程（来自 `Executed`），统一时间轴
  4. **场景触发位**——F5 上下文卡，至多 1 张，可关闭
  5. **工具宫格**——课表 / 作业 / 研讨室 / 场馆 / 活动 / 班车
- **接口** `GET /today/summary`
- **要点**
  - 待办区为空时**不要塞推荐内容**，宁可留白
  - 时间轴上"局"和"课"视觉上要能区分，但同等重要

### B2 · hermes 问答

- **路由** `/today/ask`
- **职责** 自然语言 → 校园动作（查课表、查空场、查 DDL）
- **承载** 决议一 决议三
- **区块** 对话流 + 结果卡片（结构化，不是纯文本）
- **交互**
  - 输入 → `POST /hermes/ask` → 服务端 LLM 编译为 Action Schema → 执行 → 返回结构化结果
  - 结果以**卡片**呈现（课程卡、空档卡、DDL 卡），可直接跳转对应页
- **规则**
  - **只做工具调用，不闲聊**。识别到闲聊意图时礼貌收敛并给出可做的事
  - 涉及写操作时**只给预览**，提交必须跳到正式预览页（B11 / E5）
- **红线** 不做人格养成、不主动发起对话、不做"关心"
- **要点** 这里是 hermes 与阿凑最容易被混淆的地方。**hermes 不谈"要不要找人一起"**，那是 F5 触发位和阿凑的事

### B3 · 我的课表

- **路由** `/today/timetable`
- **职责** 周视图课表
- **承载** F2 决议六
- **区块** 周切换 + 网格课表 + 本周概览
- **接口** `GET /schedule/timetable?week=N`（**走缓存**）
- **交互** 下拉刷新触发增量校验，带频率限制
- **红线** 只显示自己的课表
- **要点** 课表是缓存数据，要标注"更新于 X"，并在检测到调课时高亮

### B3.1 · 课程详情

- **路由** `/today/course/{id}`
- **职责** 单门课信息 + 同课破冰局入口
- **承载** F4
- **区块** 课程信息（含教学班）· 相关作业 DDL · **"和同课的人开个局"入口**
- **红线** **绝不显示同课同学名单**——只能开局，不能浏览人
- **要点** 入口文案用"和同课的人"，不用"和同学"，避免暗示已知名单

### B4 · 作业与 DDL

- **路由** `/today/assignments`
- **职责** 未完成作业列表，按 DDL 排序
- **承载** F5 5.3
- **接口** `GET /assignments?status=unfinished`
- **要点** 这是冲刺局的主要触发源，DDL 临近的条目要有"今晚开个冲刺局"的行动位

### B4.1 · 作业详情

- **路由** `/today/assignment/{id}`
- **职责** 作业详情 + 冲刺局入口
- **交互** "开一个 90 分钟冲刺局" → 预填意图卡跳 D3

### B5 · 体育场馆

- **路由** `/today/gym`
- **职责** 场馆查询
- **区块** 校区筛选 → 场馆类型 → 日期 → 空场展示
- **接口** `GET /venues/gym/available`
- **F5 触发** 查到有空场时展示"这个时段有场，还差一起打的人吗？"

### B5.1 · 场馆时段选择

- **路由** `/today/gym/slots`
- **职责** 选择具体时段，进入预览
- **交互** 选定 → 个人预约走 B11；带人预约走 D3（先成局）

### B6 · 图书馆研讨室

- **路由** `/today/room`
- **职责** 研讨室查询
- **区块** 房型 → 楼层 → 日期 → 空档
- **接口** `GET /venues/room/available`
- **F5 触发** "房间最多 4 人，要不要凑一支讨论小组？"
- **要点** 研讨室是组队局最强闭环，触发位权重最高

### B6.1 · 研讨室时段选择

- **路由** `/today/room/slots`
- **职责** 选定时段 → 预览
- **要点** 展示预约规则（最短/最长时长、间隔），避免选完才失败

### B7 · 活动 / 宣讲会 / 招聘会

- **路由** `/today/events`
- **职责** 活动列表
- **接口** `GET /events`（**此数据源免登录，未授权用户也能看**）
- **要点** 这是未授权用户能看到的少数真实内容，对留存很重要

### B7.1 · 活动详情

- **路由** `/today/event/{id}`
- **职责** 活动信息 + 同行/复盘局入口
- **规则** **报名跳转官方入口，不代办**（F27 红灯）
- **要点** 明确告知"报名需要你自己完成"，但"找同行"我们能做

### B8 · 组会与课题

- **路由** `/today/research`
- **职责** 组会与课题查询、预约
- **承载** F11

### B9 · 班车

- **路由** `/today/transit`
- **职责** 校内班车 + 跨校区岐关车
- **要点** 跨校区局的行程协调依赖它，F8 的通勤矩阵也来自这里

### B10 · 场景触发浮层

- **路由** 浮层，无独立路由
- **职责** F5 的实际呈现
- **承载** F5
- **规则（必须严格执行）**
  - 同一场景 N 天内不重复触发
  - 用户明确忽略 2 次 → **永久停止该场景触发**
  - 同时最多存在 1 张触发卡
  - 文案由服务端生成，客户端有兜底模板
- **要点** 触发的克制程度直接决定产品是"工具"还是"骚扰"

### B11 · 个人行动预览

- **路由** `/today/action/preview`
- **职责** hermes 的个人动作（不涉及他人）的预览与授权
- **承载** F10 决议四
- **区块** 动作摘要 · 参数明细 · 影响说明 · [授权执行] / [取消]
- **规则** 即便是个人动作，也必须走预览；**不存在跳过预览的路径**
### B12 · 赛事库 `[V2.1 新增]`

- **路由** `/today/competitions`
- **职责** 浏览经核验的比赛（黑客松、创新大赛、学科竞赛）
- **承载** F31 F5
- **区块**
  1. 筛选：方向 / 线上线下 / 报名截止时间 / 是否可组队
  2. 赛事卡片流——名称 · 截止 · 线上线下 · 赛道 · 奖励
  3. 「即将截止」置顶区
- **接口** `GET /competitions`（**免登录数据源，未授权用户可见**）
- **红线** **只展示核验状态为「可行动」的赛事**——未核验线索一律不进入客户端
- **要点**
  - 这是产品少数几个未授权也能看到真实内容的页面，对首次打开的体验很重要
  - 团队赛卡片使用「组队」；个人赛使用「找备赛搭子」，不把个人赛伪装成正式参赛队
  - 每张卡片都要有协作行动位——**每一条赛事都是一个等待被凑齐的局**

### B12.1 · 赛事详情 `[V2.1 新增]`

- **路由** `/today/competition/{id}`
- **职责** 赛事完整信息 + 组队入口
- **区块**
  1. 赛事信息：赛程（初赛/复赛/决赛）· 组队规则 · 提交要求 · 奖励
  2. 所需能力标签（来自赛道映射）
  3. **[组队] / [找备赛搭子]**——团队赛预填互补组队；个人赛预填相似备赛搭子
  4. [去官网报名]——**跳转官方入口**
- **规则** **报名不代办**（F27 红灯）。文案明确："报名需要你自己完成，我们负责帮你把队伍凑齐。"
- **要点**
  - [组队] / [找备赛搭子] 是主行动，[去报名] 是次行动，视觉权重要区分开
  - 这一页是 5.1 主场景的起点，Demo 时是高光路径的第一步

## 7. C 层 · 公开局

> 定位：**我们浏览的是局，不是人。** 这是"不做社交广场"与"需要可发现内容"之间的解法。

### C1 · 公开局列表

- **路由** `/open`
- **职责** 展示官方局与可加入的缺口卡
- **承载** F22 F23
- **区块** 筛选（校区/类型/时间/准入等级）+ 局卡片流
- **卡片内容** 目标 · 时间 · 校区 · 人数进度 · 准入等级 · 缺口角色
- **红线** 卡片上**不出现任何成员身份或等级**
- **要点** 冷启动期用免登录的宣讲会/招聘会数据填充，避免空列表

### C2 · 公开局详情

- **路由** `/open/{id}`
- **职责** 局的完整信息 + 加入
- **区块** 目标 · 时间地点 · 人数进度 · 准入门槛 · 匿名的队伍构成描述（"已有前端、产品各 1 人"）· [我来]
- **交互** [我来] → 等级校验 → 通过则进入 Pooling / Tentative；不通过跳 C3
- **红线** 队伍构成只能描述**角色**，不能描述**人**

### C3 · 准入门槛说明

- **路由** `/open/{id}/requirement`
- **职责** 等级不足时说明差什么、怎么补
- **承载** F15 F17
- **文案要点** "本局要求 T2。你还差 2 次有效成局。**最容易完成的是打球、自习、冲刺局**。"
- **要点** 这一页是**信任漏斗的转化点**——必须给出具体的、马上能做的下一步，并直接链到 D1

### C4 · 缺口卡落地页

- **路由** Universal Link `/g/{share_token}`
- **职责** 从班群/朋友圈点进来的落地体验
- **承载** F22
- **规则**
  - 未安装 App → 落地页展示卡片 + 下载引导
  - 已安装未登录 → 展示卡片，[我来] 触发认证流程，**认证后回到本卡**
  - 卡片过期 → 友好过期页 + 相似局推荐
- **要点** 这是主要的获客路径，转化链路要短

## 8. D 层 · ⊕ 差一个（阿凑）

> 定位：阿凑的入口。**在成局前积极，成局后消失。**

### D1 · 意图输入

- **路由** `/intent`
- **职责** 自然语言表达"我想干什么"
- **承载** F6
- **区块**
  1. 大输入框 + 语音输入
  2. 快捷模板：打球 / 自习 / DDL 冲刺 / 比赛组队 / 活动同行
  3. 一句示例文案轮播（降低"不知道说什么"的门槛）
- **接口** `POST /intent/compile`
- **要点** 模板不是为了省事，是为了**告诉用户这个产品能干什么**

### D2 · 澄清追问

- **路由** `/intent/clarify`
- **职责** 关键槽位缺失时追问
- **规则** **最多追问 2 轮**，之后用默认值生成草稿让用户改
- **要点** 追问超过两轮就变成了填表，违背产品的体验主张

### D3 · 意图卡确认

- **路由** `/intent/card`
- **职责** 逐项确认 AI 编译出的结构化意图
- **承载** F6
- **区块**（每字段带来源 chip）
  | 字段 | 来源 | 可编辑 |
  |---|---|---|
  | 局类型 | AI 推断 | ✓ |
  | 目标 | 用户输入 | ✓ |
  | 我的能力 | **F2/F3 预填** | ✓ 进 D3.1 |
  | 需要角色 | AI 推断 | ✓ 进 D3.3 |
  | 目标强度 | AI 推断 | ✓ |
  | 可用时间 | **F8 预填** | ✓ 进 D3.2 |
  | 校区 / 人数 | 认证事实 / AI | ✓ |
  | 社交模式 / 截止 | 默认 | ✓ 进 D3.4 |
- **埋点（关键）** **记录用户修改了哪些字段**——这是意图编译准确率的核心指标
- **要点** 预填是产品的核心体验落差。要在 UI 上让用户**感知到"我没填这些"**

### D3.1 · 能力标签编辑

- **职责** 增删能力标签
- **规则** 已验证标签**可隐藏但不可伪造**；新增标签自动标为 `自述`，并说明"自述标签在匹配中权重较低"
- **要点** 透明地告知权重差异，用户就不会试图刷标签

### D3.2 · 空档选择器

- **职责** 从系统算出的可用窗口里勾选
- **承载** F8
- **红线** 只显示自己的空档；**不显示他人任何时间信息**
- **要点** 展示的是"你有空的时段"，不是课表——不要暴露课程细节

### D3.3 · 角色需求编辑

- **职责** 组队局的角色缺口定义
- **要点** 提供该赛事/项目类型的常见角色预设

### D3.4 · 社交模式与安全偏好

- **职责** 身份公开时机、人数范围、同性局
- **承载** F26
- **要点** 安全偏好要**默认保守**（3 人及以上、满员后公开身份）

### D4 · 招募中状态

- **路由** `/intent/{id}/pooling`
- **职责** 意图已发布，等待成局
- **承载** F9
- **区块** 状态说明 · 截止倒计时 · [撤回] · 分享缺口卡入口（G2）
- **红线** **绝不显示当前报名人数或任何报名者信息**
- **文案要点** "阿凑正在帮你找人。凑不齐的话会自动结束，**不会有人知道你想去过。**"
- **要点** 这句文案是整个静默成局机制的用户感知载体，要显眼

## 9. E 层 · 我的局

> 定位：成局状态机的用户界面。**E2 是一个容器，按状态切换形态。**

### E1 · 我的局列表

- **路由** `/gatherings`
- **职责** 分段展示我参与的局与沉淀下来的搭子关系
- **分段** 待我确认 / 进行中 / 招募中 / **搭子** / 已完成
- **要点**
  - "待我确认"永远置顶且带角标——这是执行成功率的关键路径
  - **「搭子」分段刻意不做成独立 Tab**：搭子是局的沉淀，不是可以刷的内容。放进 Tab 会诱导用户去"刷人"，放在这里则强调它是共同经历的结果

### E2 · 局详情容器

- **路由** `/gathering/{id}`
- **职责** 根据状态渲染不同形态
- **状态映射**
  | 状态 | 渲染 |
  |---|---|
  | `Pooling` | D4 招募中形态 |
  | `Tentative` | **E3 确认卡** |
  | `Confirmed` / `Previewed` | **E5 行动预览与授权** |
  | `Executed` / `Active` | **E7 协作空间** |
  | `Completed` | E9 / E10 |
- **要点** 状态由服务端下发，客户端**不自行推断状态转移**

### E3 · 确认卡

- **路由** `/gathering/{id}/confirm`
- **职责** 满员后的分别确认
- **承载** F10
- **区块**
  ```
  ┌─────────────────────────────┐
  │ 局标题                       │
  │ 时间 / 地点 / 成员数（满员）   │
  │ 场地状态：可预约              │
  │ ─────────────────────────── │
  │ 为什么是你们（AI 理由）        │
  │ ─────────────────────────── │
  │ 已确认 3/4                   │
  │ [确认参加] [提议改时间] [退出] │
  └─────────────────────────────┘
  ```
- **红线** 只显示已确认**人数**，不显示是谁确认了、谁没确认
- **要点**
  - "为什么是你们"是破冰材料，要给足展示空间（F9）
  - 确认有超时；超时视为放弃但**不计入爽约**（F10），UI 上要说明这点

### E4 · 改约协商

- **路由** `/gathering/{id}/reschedule`
- **职责** 提议新时段并投票
- **区块** 服务端算出的候选时段（含可行人数）+ 投票
- **红线** 只显示"5 人中 4 人可行"，不显示谁不可行

### E5 · 行动预览与授权

- **路由** `/gathering/{id}/action`
- **职责** 多人局的校园动作预览与授权
- **承载** F10 F11 决议四
- **区块** 动作类型 · 完整参数（场地/时间/成员）· 预览快照 · [授权执行] / [提议修改]
- **规则**
  - **无预览不可执行**
  - 执行按钮在全员确认前**不可用**，并说明"等待其他成员确认"
- **要点** 这一页是产品"真正能执行"的证明，Demo 时是高光。设计上要让预约参数清晰可信

### E6 · 执行结果

- **路由** `/gathering/{id}/result`
- **职责** 执行成功/失败的反馈
- **成功** 预约凭证 · 写入日历（F12）· 进入协作空间
- **失败** 按失败类别给不同文案与下一步（场地被占 → 重新选时段；登录失效 → 重新扫码）
- **红线** 不展示任何原始报错

### E7 · 协作空间

- **路由** `/gathering/{id}/space`
- **职责** 完成这件事所必需的信息，仅此而已
- **承载** F19 F20
- **区块**
  1. 集合时间 / 地点 / 路线
  2. **AI 开场信息**（基于真实共同点，如"你们同上《人工智能》"）
  3. **群聊区**（E14）——成局后即开启
  4. 首次会议议程 / 活动规则
  5. 角色与待办
  6. 成员区（此时身份已公开）
  7. 操作：改约 / 补位 / 取消 / 举报
  8. **阿凑退场提示**
- **红线** 无动态流、无个人主页、无任何鼓励持续刷的设计
- **要点**
  - 阿凑在这里要**明显地退场**——一条退场消息后，AI 气泡视觉上淡化
  - 之后阿凑只在四种情况出现：提醒、改约、补位、被 @
  - **布局要传达"位置让给人"**：退场后协作信息收拢为顶部一条，群聊占据主体面积

### E8 · 补位面板

- **路由** `/gathering/{id}/backfill`
- **职责** 缺口回到匹配池
- **承载** F13
- **规则** 补位者**不回溯此前的协作记录**
- **要点** 补位失败时给降级方案（双打改练球、4 人改 3 人），方案是预置规则不是 LLM 自由发挥

### E9 · 完成确认

- **路由** `/gathering/{id}/complete`
- **职责** 局后确认是否真的完成
- **承载** F18
- **区块** "这次局完成了吗？" + 极简反馈
- **要点** 这是到场验证的行为代理，**不要做成评分**——不评价人，只确认事

### E10 · 复局选择

- **路由** `/gathering/{id}/recur`
- **职责** F21 的三个选项
- **区块** [原班复局] / [保留部分成员，再差一个] / [结束]
- **红线** 选"结束"后**双方都不会知道**，无任何通知
- **要点** 复局是最强正向信号（F18），入口要显眼

### E11 · 共同目标

- **路由** `/goal/{id}`
- **职责** 长周期目标的进度追踪
- **承载** F21
- **区块** 目标 · 进度（**自动更新**）· 成员进度 · 下次行动 · AI 播报
- **规则** 掉队提醒发给**其他成员**，措辞不得羞辱
- **要点** 进度尽量由预约/到场记录自动更新，减少手动打卡

### E12 · 退出 / 取消确认

- **路由** 弹层
- **承载** F18
- **文案要点** 提前取消**明确告知不影响信任等级**——这直接决定用户是"好好取消"还是"直接不出现"
- **要点** 临期退出要额外确认，并说明影响

### E13 · 举报与拉黑

- **路由** `/gathering/{id}/report`
- **承载** F26
- **规则** 常驻可见；一次有效举报**永久切断双方匹配链路**
- **要点** 入口必须好找，但不能太显眼到暗示"这里很危险"

### E14 · 局内群聊 `[V2.1 新增]`

- **路由** `/gathering/{id}/chat`（也内嵌于 E7）
- **职责** 局成员之间的真实对话通道
- **承载** F28 F20
- **区块**
  1. 消息流（文本 / 图片 / 位置）
  2. 输入区
  3. **@阿凑** 唤起（唯一让 AI 重新出现的入口）
  4. 顶部收拢的局信息条（时间地点，一行）
- **交互**
  - 成局确认后开启，招募期**不可用**
  - `@阿凑` 触发工具调用（订场、查资料、加日程），**用完即退**，不参与后续对话
- **红线（逐条对应 F28）**
  - ❌ 已读回执 ❌ 在线状态 ❌ 正在输入
  - ❌ 拉人进群 ❌ 群二维码 ❌ 表情包商店 / 虚拟礼物
  - ❌ 消息数量角标做成红点轰炸（用弱提示）
- **要点**
  - 这是产品里**唯一鼓励用户多停留的地方**，但停留的对象是人不是 AI
  - 阿凑的消息与人的消息要有明确视觉区分，且阿凑消息默认折叠为一行

### E15 · 搭子关系列表 `[V2.1 新增]`

- **路由** `/companions`（E1 的一个分段）
- **职责** 展示共同完成过局的关系
- **承载** F29
- **区块** 关系卡片流，每张卡片：
  ```
  ┌─────────────────────────────┐
  │ 3 人 · 羽毛球                │
  │ 一起打过 4 次，最近 3 周前     │
  │ [再来一次]      [进入对话]    │
  └─────────────────────────────┘
  ```
- **红线**
  - **无加好友按钮、无搜索框、无推荐关系**
  - **不排序为排行榜**，按最近共同经历时间倒序即可
  - 卡片上不出现任何评价性描述
- **要点** 卡片的主行动是 **[再来一次]** 而非 [聊天]——**这是关系页而不是通讯录的关键**，它把入口指向"再做一件事"

### E16 · 搭子关系详情 `[V2.1 新增]`

- **路由** `/companion/{relation_id}`
- **职责** 一段关系的共同经历 + 对话 + 复局入口
- **承载** F29 F21
- **区块**
  1. **共同经历时间线**——做过什么、几次、什么时候、结果（**全部自动生成**）
  2. 共同点（同上的课、共同的跨专业方向）
  3. 进行中的共同目标进度（若有）
  4. 对话区
  5. [再来一次] / [解除关系]
- **红线**
  - 时间线只记**事实**，绝不出现"靠谱""话多""迟到"等任何评价
  - 双方看到的内容必须**完全一致**
- **要点** 这一页是判断二的可视化证据——**"你们一起完成了 4 件事"比任何标签都更能说明关系**

### E17 · 解除关系 `[V2.1 新增]`

- **路由** 弹层
- **承载** F28-5 F29
- **规则**
  - 单方面可解除，**对方不会收到任何通知**（与 F21「结束」一致）
  - 解除后对话通道关闭、共同经历从双方视图移除
  - 文案明确告知"对方不会知道"
- **要点** 无痛退出机制是产品的核心承诺之一，这里不能有任何挽留式设计

## 12. G 层 · 全局

### G1 · hermes 唤起浮层
- 全局可唤起的问答入口，受 F20 约束（成局后不主动出现）

### G2 · 缺口卡分享 Sheet
- **承载** F22
- 生成卡片图 + 深链，支持微信/朋友圈/系统分享
- **红线** 卡片上不含分享者身份

### G3 · 重新扫码授权浮层
- 会话失效时的统一处理
- **规则** 不阻断浏览与匹配，仅在执行动作时提示

### G4 · 静默解散处理
- **承载** F9-3
- **规则** 不发失败通知，或只发极弱中性通知："这次没凑齐，已为你留意周六下午"
- **红线** 文案中**不得出现任何归因到人的表述**

### G5 · 空 / 错 / 加载态规范
- 空态：说明 + 一个可行动的下一步，**不塞推荐内容**
- 错误态：归一化的五类错误对应五套文案，不展示原始报错
- 加载态：超过 1s 用骨架屏；超过 5s 给可取消入口

## 14. 缓存策略

| 数据 | 策略 | 失效 |
|---|---|---|
| 课表 | SwiftData 长期缓存 | 每周增量校验 / 手动下拉 |
| 画像与能力标签 | 长期缓存 | 编辑后即时更新 |
| 局列表与详情 | 短缓存 60s | 状态变更推送后失效 |
| 场地空档 | **不缓存** | 实时性要求高 |
| 信任等级 | 缓存至下次启动 | 成局完成后失效 |
| 会话令牌 | **Keychain** | 不入 SwiftData |

## 15. 推送类型

| 类型 | 触发 | 深链 |
|---|---|---|
| 待确认 | 局进入 `Tentative` | E3 |
| 待授权 | 进入 `Previewed` | E5 |
| 执行成功 | `Executed` | E6 |
| 局前提醒 | T-24h / T-2h | E7 |
| 补位邀请 | 缺口回池 | C2 |
| 静默解散 | 未满员 | **中性文案，无深链** |
| 重新授权 | 会话失效 | G3 |
| 等级变化 | 升级/降级 | M3 |
| **群聊消息** | 局内或搭子对话有新消息 | E14 / E16 |

> **明确不发的推送**（违背 F20 / F30）：
> - 任何"关心你"、"好久没来"、"有新用户加入"类召回
> - **基于共同经历的召回**："你们好久没一起打球了""你和 XX 的这一年"
> - 群聊的高频轰炸——同一会话的消息推送要合并与限频

## 16. 埋点与指标映射

| 指标（第七部分） | 客户端埋点 |
|---|---|
| 有效成局数 | 状态流转至 `Executed` |
| 成局中位耗时 | D4 发布时间 → E3 全员确认时间 |
| 多人确认率 | E3 确认 / 满员局数 |
| 执行成功率 | E6 成功 / E5 授权数 |
| 30 日复局率 | E10 原班复局 |
| **意图编译准确率** | **D3 字段修改率**（关键） |
| AI 退场成功率 | E7 内 24h 人际互动次数 |
| **人际对话发生率** | **E14 成局后 24h 内是否产生双向对话（布尔，不计数）** |
| F5 触发有效性 | B10 展示 / 点击 / 忽略 |

**不埋的**：AI 对话时长、**人际对话时长与消息条数**、卡片浏览数、搭子数量。

> 对话只埋**是否发生**，绝不埋**多寡**。这些指标一旦存在就会有人去优化它，
> 而优化对话量必然长出让人多聊的机制——那正是 0.4 反对的方向。
